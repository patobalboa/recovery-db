ADMINISTRACIÓN DE BASE DE DATOS · AWS ACADEMY

EXPEDIENTE DBA 003 · RECOVERY DB

Operación de PostgreSQL, respaldo, recuperación y optimización en EC2

Modalidad: trabajo práctico individual o en parejas. Entorno: servidor Linux sobre AWS Academy Learner Lab. Duración: 180 minutos de trabajo inicial, con posible continuidad fuera de clase para completar mediciones e informe. Entrega: informe técnico PDF con evidencias.

Tu misión

NovaStore opera una base de datos PostgreSQL con clientes, productos y pedidos. Un error de mantenimiento provoca pérdida de información; simultáneamente, algunas consultas comerciales presentan bajo rendimiento. Tu equipo es responsable de poner en marcha la infraestructura, demostrar que puede recuperarse y justificar mejoras de rendimiento medibles.

Repositorio del laboratorio: github.com/patobalboa/recovery-db.

Norma: no se entregan soluciones de respaldo, restauración ni índices. Debes investigarlas, ejecutarlas y defender tus decisiones usando documentación oficial.

1. Lo que aprenderás

  1. Implementar PostgreSQL en una instancia EC2 y verificar el servicio, almacenamiento y seguridad.
  2. Administrar bases, esquemas, tablas, roles y conexiones mediante herramientas nativas.
  3. Seleccionar y probar una estrategia de respaldo y recuperación confiable.
  4. Demostrar integridad tras una recuperación y analizar RPO/RTO.
  5. Investigar consultas SQL con EXPLAIN (ANALYZE, BUFFERS), plantear hipótesis e implementar una mejora justificada.

2. Preparación en AWS Academy

  1. Inicia Learner Lab y verifica sus restricciones y recursos disponibles.
  2. Despliega una EC2 Ubuntu Server apropiada para el laboratorio. Registra región, AMI, tipo de instancia, vCPU/RAM y tamaño de EBS.
  3. Configura acceso SSH exclusivamente desde tu dirección o red indicada. No abras PostgreSQL/5432 a Internet.
  4. Ingresa por SSH. Investiga e instala PostgreSQL y Git usando fuentes oficiales para la versión de Ubuntu disponible.
  5. Identifica: versión del servidor, estado del servicio, puerto, ubicación del cluster, ruta de configuración, espacio en disco y métodos de autenticación.
  6. Crea una bitácora con comandos, hipótesis, errores observados y evidencias. No publiques contraseñas ni archivos .pem.

Pistas de exploración: systemctl, psql --version, ss, df, lsblk, documentación de pg_hba.conf y postgresql.conf. Elige los comandos que respondan a tus preguntas; explica por qué.

Pregunta de estudio: ¿por qué tener acceso SSH no significa que el puerto 5432 deba estar abierto desde Internet?

3. Preparación de la base NovaStore

  1. Clona el repositorio con git clone https://github.com/patobalboa/recovery-db.git.
  2. Revisa primero sql/01_esquema.sql e identifica tablas, dependencias, claves primarias y foráneas.
  3. Crea una base nueva y exclusiva para tus pruebas; elige su nombre y registra la decisión.
  4. Ejecuta el esquema y posteriormente sql/02_datos.sql. Si tu EC2 tiene poca RAM o espacio, estudia el parámetro de escala del generador.
  5. Utiliza sql/04_integridad.sql para registrar una fotografía inicial de registros, relaciones y tamaño de base.
  6. Comprueba que los resultados coinciden con las estructuras que esperabas. Si existen errores, no los ocultes: incorpóralos a la bitácora.

Pregunta: ¿qué pruebas mínimas permiten afirmar que una base está correctamente poblada? ¿Por qué una captura de una tabla no basta?

4. Misión de respaldo

  1. Consulta los enfoques de respaldo lógico y físico. Elige el más apropiado para este ejercicio y fundamenta.
  2. Investiga la documentación de pg_dump, pg_restore y los formatos disponibles.
  3. Decide ubicación, nombre, alcance y permisos del archivo. ¿Qué ocurriría si se pierde la EC2?
  4. Realiza el respaldo; registra duración, tamaño y un checksum.
  5. Inspecciona el resultado y explica qué componentes podrían quedar fuera (por ejemplo, determinados objetos globales).

Entregable de fase: evidencia del backup, su checksum, justificación de formato y procedimiento documentado. No subas dumps de gran tamaño ni contraseñas.

5. Misión de recuperación

Una vez que tengas un artefacto verificable, el docente indicará un incidente controlado sobre tu base de laboratorio.

  1. Captura estado sano, hora, recuentos y consultas relevantes.
  2. Simula solo el incidente autorizado. No borres la EC2, su EBS ni otras bases.
  3. Registra el problema observable e investiga cómo restaurar el formato generado.
  4. Restaura en una base de destino distinta de la utilizada para el incidente, de modo que conserves evidencia.
  5. Vuelve a ejecutar las consultas de integridad y compara con tus valores iniciales.
  6. Calcula el tiempo efectivo de recuperación y explica el posible punto de pérdida de datos.

Preguntas: ¿qué diferencia hay entre RTO y RPO? ¿Por qué tener un respaldo en disco no equivale a probar una restauración? ¿Qué sucede con operaciones posteriores al backup?

6. Misión de optimización SQL

El área comercial denuncia que el historial de clientes y los reportes de ventas son demasiado lentos.

  1. Abre sql/03_consultas.sql y selecciona al menos dos consultas para estudiar.
  2. Obtén el plan inicial real con EXPLAIN (ANALYZE, BUFFERS); registra duración, filas reales/estimadas, operaciones y buffers.
  3. Formula una hipótesis concreta: ¿dónde está el costo? ¿Qué alternativa podrías probar?
  4. Realiza solo un cambio a la vez y conserva la sentencia empleada para poder revertirlo.
  5. Vuelve a medir la misma consulta, en la misma EC2, con el mismo dataset y condiciones comparables; repite mediciones.
  6. Analiza si mejoró, empeoró o quedó igual. Considera tamaño de índices, costo de escrituras y riesgos de mantenimiento.

Importante: EXPLAIN ANALYZE ejecuta la sentencia; aplícalo a consultas de lectura durante este ejercicio. Un Seq Scan no siempre es incorrecto y un índice no siempre mejora la consulta.

7. Material para estudiar antes y durante el laboratorio

  • Using EXPLAIN (análisis de planes reales).
  • Indexes (trade-offs).

  • AWS EC2 — Security Groups (alcance de reglas).
  • Bibliografía ampliada y autoevaluación del repositorio.

8. Evidencias e informe final

Adjunta un PDF con: arquitectura AWS, instalación y seguridad de PostgreSQL, descripción del modelo, conteos de integridad, estrategia de respaldo, verificación y checksum, incidente simulado, recuperación comparada, RPO/RTO, planes y mediciones de dos consultas, hipótesis, cambios realizados, riesgos y bibliografía. Usa la plantilla de informe y la bitácora.

Rúbrica (100 pts): AWS y seguridad 15; modelo e integridad 10; respaldos 20; recuperación 25; optimización 20; informe 10. Ver detalle.
